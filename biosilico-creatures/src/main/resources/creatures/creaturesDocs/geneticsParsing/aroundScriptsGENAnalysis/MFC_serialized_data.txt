MFC serialized data is used in Creatures 1 and Creatures 2 for saved worlds (.sfc files) and creatures (.exp files). Similar to CreaturesArchive data, it contains serialized objects from the game engine, essentially an on-disk representation of the internal game state. Objects are serialized using the built-in Windows MFC serialization routines.

Although the format is not fully understood, openc2e is capable of extracting enough data from SFC files to enable default worlds (or any without creatures present) to be loaded almost entirely. Its source code contains a Python script for doing this, as well as the C++ code used by the engine itself.

SFC files[edit]

SFC files (.sfc) are the world save format for Creatures 1 and Creatures 2. They contain all modifiable information about worlds - such as rooms, agents and creatures.

The default world - which the Emergency Kit and World Switcher use to reset or make a new world - is stored in Eden.sfc, and the current world in World.sfc - although you can also use different files if you're using cheats or the World Switcher. Third-party worlds come with their own SFC files.
EXP files[edit]

EXP files (.exp) are files for exported creatures in Creatures 1 and Creatures 2. EXP files include a snapshot of the chemical condition of the norn, the genetic D-DNA, the state of the norn brain and information about pregnancies. A common trick for preserving the original exp file in Creatures 1 was to open its properties and check 'read-only'. The game would not then delete the original file upon importing the creature, although it made the game hang a bit.
Common structures[edit]

MFC serialized data is a dump of binary engine data, with most objects serialized with a CArchive header.
[edit]

Objects serialized through CArchive start with a header which specifies whether the object is:
type 	description
uint16 	persistent id
uint32 	32-bit persistent id (only if 16-bit persistent id == 0x7FFF)

If the persistent id is 0, this is a NULL object.

If the persistent id is -1 (0xFFFF), then this is a new object using a new class, specified by the following:

If the persistent id is not -1 and persistent_id & 0x8000 is not empty, then this is a new object using an already-seen class at persistent_id & ~0x8000.
type 	description
uint16 	schema number
uint16 	class name length
... 	class name in ASCII

If the persistent id is anything else, then it is a reference to an already-seen object.

New persistent ids are assigned whenever a new class is seen, and whenever a new object is seen (if both, then the new class is assigned an id first).

Creatures 1 Vehicle[edit]

Subclass of CompoundObject:
type 	description
int32 	xvel (fixed-point 24.8)
int32 	yvel (fixed-point 24.8)
int32 	xpos (fixed-point 24.8)
int32 	ypos (fixed-point 24.8)
uint32 	cabin left
uint32 	cabin top
uint32 	cabin right
uint32 	cabin bottom
uint32 	bump

Vehicles store their velocity and an extra position variable (besides the normal Object position) as fixed-point 24.8 fractional numbers, which have a 24-bit integer part and an 8-bit fractional part. These can be truncated to integers via value >> 8, or converted to floating-point numbers via value / 256.0. They can be created from integers via ivalue << 8.

These are used in the following situations:

    Every tick, vehicles update their fixed-point position based on their velocity. If the new position doesn't collide with anything, then the Object integer position is set to the truncated fixed-point position.
    On valid Activate1, Active2, or Deactivate events, the fixed-point position is reset to be equal to the Object integer position.

Creatures 1 Lift[edit]

Subclass of Vehicle:
type 	description
uint32 	number of floors
uint32 	next or current floor
int32 	current call button
uint8 	delay counter
{uint32, CallButton}[8] 	y-position for floor i, and arbitrary activated callbutton slot i.

This is very silly. Here's what's going on with the last field: there are up to 8 floors, and thus also up to 8 activated callbuttons. Unfortunately these do not share the same order but are paired together for serialization. lift_data_items[i].floor_y is simple, it's the y-position for floor #i. However, lift_data_items[i].activated_callbutton_slot is unrelated to floor #i. The lift treats these as an arbitrary set of activated callbuttons that it can scan through to find its next floor (finding the callbutton's floor indirectly by looking at its floor id and then reindexing back into the lift's own data).

Creatures 1 BodyPart[edit]

Subclass of Entity:
type 	description
uint32 	angle (the current calculated angle from the pose string)
uint32 	view (the current calculated sprite pose, based on the angle and direction but not including head adjustments for moods or closed eyes)

Some examples:

    Sid.exp's head has an angle of 4 (towards camera), a view of 8 (towards camera), a gallery named 4AFX with a base offset of 0, and using sprite 21 (offset 0 + view 8 + normal mood 0 + closed eyes 13).
    Vixy.exp's left thigh has an angle of 3 (upward), a view of 7 (upward, west-facing), a gallery named 5TSF with a base offset of 36, and using sprite 43 (offset 36 + view 7).

Creatures 1 Body[edit]

Note that the body attachment data is transposed compared to ATT files! ATT files are written such that each pose/angle of the body is in order, with all attachment data for all body parts for that pose. MFC-serialized body data instead has each body part in order, with all attachment data for every pose for that part.
